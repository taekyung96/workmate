# ADR-0006. 분산 상태를 Redis 로 옮긴다 (세션 · SessionRegistry · 레이트리밋)

- **상태**: 채택
- **맥락 문서**: [검증 리포트](../../features/redis/REPORT-2026-09-02.md) · [12. 운영 가이드](../../development/12_OPERATIONS.md)
- **관련 ADR**: [ADR-0001](0001-hybrid-ssr-to-vue3-spa.md)(세션 인증·WAS 은닉)

## 맥락 (Context)

인증과 남용 방지에 쓰이는 상태 세 가지가 **각 JVM 의 힙 안**에 있었다.

| 대상                                       | 위치                  | 모듈           |
| ------------------------------------------ | --------------------- | -------------- |
| HTTP 세션                                  | 톰캣 인메모리         | `workmate-web` |
| `SessionRegistry` (F1-08 중복 로그인 차단) | `SessionRegistryImpl` | `workmate-web` |
| `ChatRateLimiter` (F2-11 분당 한도)        | `ConcurrentHashMap`   | `workmate-was` |

단일 인스턴스에서는 아무 문제가 없다. 문제는 **인스턴스를 늘리는 순간 셋 다 깨지는데,
예외도 에러 로그도 남지 않는다**는 것이다. 로그만 봐서는 정상으로 보인다.

실제로 재현해서 쟀다([리포트](../../features/redis/REPORT-2026-09-02.md)):

| 항목             | 인스턴스 2개일 때                                                                          |
| ---------------- | ------------------------------------------------------------------------------------------ |
| 세션             | 다른 인스턴스로 요청이 가면 **401** — 사용자는 이유 없이 로그아웃된다                      |
| 중복 로그인 차단 | 같은 계정의 **두 세션이 동시에 살아남는다.** 인스턴스마다 "이 사용자 세션 1개"를 따로 센다 |
| 레이트리밋       | 한도 5 에 **10건이 통과**했다 — 정확히 인스턴스 수만큼 곱해진다                            |

②가 특히 위험하다. 계정 도용에 대응해 세션을 끊었다고 생각해도 다른 인스턴스에서는
그대로 살아있다. **보안 기능이 무음으로 무력화된다.**

이 문제는 원래 "k3s 로 옮겨 무중단 배포를 붙일 때" 다룰 예정이었으나(완결 체크리스트 Phase 2),
**부하 테스트보다 먼저** 하기로 앞당겼다. 순서를 지켜야 "도입 전/후"를 숫자로 비교할 수 있고,
compose 에서 `--scale` 만으로도 같은 문제가 재현되므로 k3s 를 기다릴 이유가 없다.

## 결정 (Decision)

**Redis 인스턴스 하나를 WEB·WAS 가 공유하고, 세 가지 상태를 모두 그리로 옮긴다.**

### D1. 하나의 Redis, 키 네임스페이스로 분리

```
workmate:session:*     (WEB — Spring Session 이 관리)
workmate:ratelimit:*   (WAS — ChatRateLimiter)
```

두 모듈이 공유하는 Java 코드는 없다. 각자 붙고, 섞이지 않게 프리픽스로만 나눈다.
인스턴스를 둘로 나누면 운영 대상이 하나 더 늘 뿐 얻는 게 없다.

배포에서는 **호스트에 6379 를 열지 않는다** — WAS 를 내부망에 두는 [ADR-0001](0001-hybrid-ssr-to-vue3-spa.md)과 같은 원칙이다.
`appendonly yes` 를 켠다. 세션이 여기 있으므로 재시작에 전부 날아가면 로그인한 사용자가 모두 튕긴다.

### D2. `SpringSessionBackedSessionRegistry` — `repository-type: indexed` 가 필수다

세션만 Redis 로 옮기고 `SessionRegistryImpl` 을 그대로 두면 ①만 고쳐지고 ②는 그대로 깨진 채 남는다.
레지스트리도 Redis 를 보게 바꿔야 한다.

```yaml
spring:
    session:
        store-type: redis
        redis:
            namespace: workmate:session
            repository-type: indexed # ← 이게 없으면 F1-08 이 조용히 죽는다
```

**`indexed` 가 아니면 사용자별 세션 인덱스(`PRINCIPAL_NAME_INDEX_NAME`)가 만들어지지 않아
레지스트리가 특정 사용자의 세션들을 찾지 못한다.** 앱은 정상 기동하고 에러도 없다. 중복 로그인 차단만 안 될 뿐이다.

이 함정을 막으려고 **빈 타입을 단언하는 테스트**를 뒀다(`RedisSessionConfigTest`).
누군가 `SessionRegistryImpl` 을 다시 등록하면 이 테스트가 깨진다.

### D3. 레이트리밋은 Lua 가 아니라 `INCR` + 키에 분(minute)을 넣는다

`INCR` 은 그 자체로 원자적이라 카운터 증가에는 경합이 없다. 문제는 `INCR` 과 `EXPIRE` 사이다 —
그 틈에 프로세스가 죽으면 TTL 없는 키가 영원히 남는다.

보통 Lua 스크립트로 두 명령을 묶어 해결하지만, **키 이름에 분을 넣으면 그럴 필요가 없다.**

```
workmate:ratelimit:{userSeq}:{minute}
```

그 키는 다음 분에 다시 쓰이지 않으므로, TTL 이 빠진 키가 남더라도 **판정에 영향을 주지 않는다.**
쓰레기가 쌓이지 않게 첫 증가에서만 `EXPIRE`(90초)를 건다.

덤으로 인메모리 구현의 결함 하나가 해소된다 — 기존 `ConcurrentHashMap` 은 `userSeq` 키를
한 번도 지우지 않아 사용자 수만큼 힙이 단조 증가했다.

### D4. 실패 정책을 대상별로 반대로 잡는다

| 대상       | 정책                                               | 이유                                                                                 |
| ---------- | -------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 세션       | **fail-closed** — Redis 가 죽으면 기동/로그인 불가 | 인증이다. 못 믿으면 막는 게 맞다                                                     |
| 레이트리밋 | **fail-open** — 경고 로그만 남기고 통과            | 남용 방지 장치이지 인증이 아니다. Redis 장애로 채팅 전체를 막으면 장애 범위가 커진다 |

**이 선택에는 대가가 있다.** 검증 중 실제로 드러났다 — compose 에 `REDIS_HOST` 를 빠뜨렸더니
WEB 은 기동 자체가 실패해 즉시 알았지만, **WAS 는 아무 이상 없이 떴다.**
레이트리밋이 사실상 꺼진 상태였는데 로그에 흔적이 없었다.

fail-open 을 유지하되, **레이트리밋 실패율을 지표로 노출하는 것**을 후속 과제로 남긴다.
지금은 `log.warn` 만 남긴다.

### D5. 테스트는 Testcontainers 를 쓰지 않고 compose Redis 에 붙는다

Gradle 테스트 JVM 은 Windows 프로세스인데 Docker 데몬은 WSL2 안에 있다.
Windows 쪽에 `docker.exe` 도 npipe 도 없어 Testcontainers 가 데몬을 찾지 못한다
(`Could not find a valid Docker environment`). TCP 리스너를 열려면 `sudo` 로 개발 PC 설정을
바꿔야 하는데, 테스트 하나 때문에 그럴 이유가 없다.

**이 프로젝트는 이미 같은 문제를 다르게 풀고 있었다.** `application-local.yml` 은
`jdbc:postgresql://localhost:5432/workmate_db` 로 WSL2 의 compose PostgreSQL 에 붙는다.
WSL2 가 published 포트를 Windows localhost 로 포워딩해 주기 때문이다.

Redis 도 같은 방식을 쓴다. compose 가 `6379:6379` 로 열고, 테스트는 `localhost:6379` 에 붙는다.
**CI 의 service 컨테이너도 같은 주소**라 로컬과 CI 가 같은 코드로 돈다.

대가는 "이 테스트들은 Redis 가 떠 있어야 돈다"인데, 기존 DB 통합 테스트와 같은 조건이라
새로 생기는 제약이 아니다. Redis 에 못 붙으면 **조용히 스킵하지 않고 실패**시킨다
(`@Disabled`·`assumeTrue` 금지) — 스킵되면 분산 레이트리밋이 깨져도 아무도 모른다.

## 고려한 대안 (Alternatives)

| 대안                                                  | 기각 이유                                                                                                                                          |
| ----------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| **스티키 세션** (LB 가 같은 사용자를 같은 인스턴스로) | 세션은 가려지지만 **중복 로그인 차단과 레이트리밋은 그대로 깨진다.** 인스턴스가 죽으면 그 사용자들이 전부 로그아웃된다. 로드밸런서에 의존이 생긴다 |
| **DB 세션** (`spring-session-jdbc`)                   | 새 인프라가 필요 없다는 게 장점이나, 매 요청마다 PostgreSQL 에 부하를 더한다. DB 는 이미 pgvector 검색을 감당하고 있다                             |
| **Hazelcast** 등 인메모리 그리드                      | 의존성이 무겁고 JVM 간 클러스터링 설정이 붙는다. 얻는 것 대비 운영 복잡도가 크다                                                                   |
| **k3s 로 옮길 때 함께 처리** (원래 계획)              | 부하 테스트가 먼저 필요한데, 그러면 "도입 전/후" 비교 수치를 못 만든다. compose `--scale` 로 충분히 재현되므로 기다릴 이유가 없다                  |

## 결과 (Consequences)

### ➕ 얻은 것

- 인스턴스를 늘려도 셋 다 정상 동작한다 — [리포트](../../features/redis/REPORT-2026-09-02.md)에서 전후 수치로 확인
- 레이트리밋 키 누수가 해소됐다(TTL 90초)
- **부하 테스트를 의미 있게 할 수 있게 됐다.** 인스턴스를 늘려도 기능이 안 깨지므로 수평 확장 자체를 측정할 수 있다

### ➖ 치른 것

- **운영 대상이 하나 늘었다.** Redis 가 죽으면 로그인이 안 된다(D4 의 fail-closed)
- 테스트가 Redis 기동에 의존한다(D5)
- **레이트리밋 오설정이 조용히 넘어갈 수 있다**(D4) — 지표 노출이 후속 과제

### 남은 것

- 레이트리밋 fail-open 발생률을 Prometheus 지표로 노출
- Redis 자체의 가용성(단일 인스턴스다) — 지금 규모에서는 과한 투자라 다루지 않는다
- **WEB→WAS 신원 전달은 이번 작업으로 해결되지 않았다.** `X-User-Seq` 는 여전히 서명 없는 평문 헤더이고,
  WAS 인스턴스가 늘어난 만큼 재검토 시점이 가까워졌다([HANDOVER 알려진 한계](../HANDOVER.md) 참고)
