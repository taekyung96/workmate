# ADR-0004. 브랜치 전략 — GitHub Flow 채택 (Git Flow·develop 기각)

- **상태**: 채택
- **맥락 문서**: [CI 워크플로](../../../.github/workflows/ci.yml) · [아키텍처](../../development/01_ARCHITECTURE.md)
- **관련 ADR**: [ADR-0001](0001-hybrid-ssr-to-vue3-spa.md)

## 맥락 (Context)

그동안 `main` 브랜치에 직접 커밋해 왔다. 1인 개발이라 당장 충돌은 없었지만 두 가지 문제가 있었다.

1. **CI 의 절반이 놀고 있었다.** 워크플로는 `push: [main]` 과 `pull_request: [main]` 양쪽에 걸려 있는데,
   PR 을 만들지 않으니 PR 경로가 한 번도 실행되지 않았다.
2. **검증 전 코드가 곧바로 `main`** 이 된다. `main` 에 푸시되면 GHCR 이미지가 만들어지므로,
   깨진 커밋이 그대로 배포 후보가 된다.

브랜치 전략을 도입하기로 하고, 어떤 것을 쓸지 결정해야 했다.

## 결정 (Decision)

**GitHub Flow 를 채택한다.**

```
main (항상 배포 가능)
 └─ feat/xxx  작업 → push → PR → CI 통과 확인 → 머지 → 브랜치 삭제
```

- 브랜치 이름은 커밋 컨벤션과 맞춘다 — `feat/` · `fix/` · `docs/` · `chore/` · `refactor/`
- 작업 브랜치는 **짧게** 유지한다. 오래 살수록 `main` 과 벌어져 머지가 위험해진다
- `main` 머지 = 배포 후보 확정. 그래서 `publish` 잡은 `main` 푸시에서만 돈다

## 고려한 대안

| 대안                             | 기각 이유                                                                                         |
| -------------------------------- | ------------------------------------------------------------------------------------------------- |
| **Git Flow** (`develop` 포함)    | 릴리스 브랜치에서 배포를 준비하는 모델. 여기선 **머지가 곧 배포**라 `release/*` 가 할 일이 없다   |
| **`develop` 통합 브랜치만 추가** | 통합할 상대가 없다(1인). 머지가 두 번이 되고, `develop` 에도 CI 를 걸지 않으면 검증 공백이 생긴다 |
| **환경 브랜치**(GitLab Flow)     | staging 환경이 아직 없다. 생기면 그때 재검토한다                                                  |
| **`main` 직접 커밋 유지**        | PR 경로 CI 가 계속 놀고, 깨진 커밋이 바로 배포 후보가 된다                                        |

### `develop` 을 두지 않은 이유

`develop` 이 값을 하는 조건은 넷인데, 이 프로젝트는 **하나도 해당하지 않는다.**

| 조건                                      | 현재 |
| ----------------------------------------- | :--: |
| 여러 명이 병렬 작업 → 공용 통합 지점 필요 |  ❌  |
| 릴리스를 모아 버전으로 찍음               |  ❌  |
| staging 환경이 `develop` 을 바라봄        |  ❌  |
| 완성 기능을 운영에 안 내보내고 붙잡아둠   |  ❌  |

"`main` 이 깨질까 봐"가 `develop` 의 흔한 동기인데, 그 역할은 **PR + CI + 브랜치 보호**가 이미 한다.
같은 보호를 두 겹으로 치는 것이지 검증 강도가 올라가지 않는다.

> Git Flow 는 2010년에 제안됐고, **저자 본인이 이후 "지속 배포하는 웹앱에는 과하다"는 취지의 주석을 덧붙였다.**

## 결과 (Consequences)

- ➕ **PR 경로 CI 가 실제로 동작한다.** 머지 전에 프론트 타입체크·테스트, WAS/WEB 통합 테스트가 돈다
- ➕ **검증과 배포가 분리된다.** PR 에서는 테스트만, `main` 머지에서만 GHCR 이미지 생성
- ➕ PR 이력이 남아 변경 단위와 근거를 나중에 되짚을 수 있다
- ➖ 1인 작업에 절차가 한 단계 늘어난다. 작은 변경도 브랜치를 파야 한다
- ➖ `main` 브랜치 보호(상태 검사 필수)를 걸지 않으면 규율이 강제되지 않는다 — **후속 과제**

## 후속 과제

- [ ] GitHub 저장소 설정에서 `main` 에 **"CI 통과해야 머지 가능"** 규칙 적용
      (Settings → Rules → Rulesets → Require status checks to pass)
- [ ] staging 환경이 생기면 환경 브랜치(GitLab Flow) 도입 여부 재검토
