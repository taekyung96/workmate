# ADR-0003. WAS 수정 허용(무변경 원칙 완화) & 가이드 관리자 권한

- **상태**: 채택 (ADR-0001의 "WAS 무변경" 항목을 완화·부분 대체)
- **맥락 문서**: [아키텍처 상세](../../development/01_ARCHITECTURE.md) · [백엔드 가이드](../../development/04_BACKEND_GUIDE.md)
- **관련 ADR**: [ADR-0001](0001-hybrid-ssr-to-vue3-spa.md)

## 맥락 (Context)

ADR-0001은 v3 재설계 시 **"WAS는 v2에서 복사해 무변경"** 을 원칙으로 삼았다. AI 백엔드(주인공)를 보호하고, v3의 변화를 프론트(신규 SPA)와 WEB(얇은 BFF 전환)에 국한하려는 의도였다.

그러나 실제 기능 개선 과정에서 이 원칙이 걸림돌이 되는 사례가 나왔다. 대표적으로 **가이드 문서 수정·삭제를 관리자에게도 허용**하려 할 때다.

- WAS는 사용자 식별을 `X-User-Seq` 헤더만 받고, 소유자 검증(`findOwnedGuide`)은 오직 `userSeq` 일치만 본다. **관리자를 판별할 정보 자체가 WAS로 전달되지 않았다.**
- "무변경"을 지키려고 **프론트에서 버튼만 관리자에게 노출**하면, WAS가 여전히 소유자만 통과시켜 관리자가 눌러도 실패한다. 즉 화면과 실제 동작이 어긋나고, 최종 방어선(서버)이 프론트 노출 기준과 불일치하게 된다.

경직된 "무변경"은 **보안 방어선을 프론트로 떠넘기는 우회**를 유도한다. 원칙을 현실에 맞게 조정할 필요가 생겼다.

## 결정 1 — WAS "무변경" → "최소·신중한 변경" 으로 완화

- WAS는 여전히 **주인공이자 보호 대상**이다. 초기 세팅은 v2에서 그대로 복사한다.
- 다만 **기능상·보안상 필요하면 WAS도 수정할 수 있다.** "무변경"을 절대 규칙으로 두지 않는다.
- 변경은 신중히: 3-tier·네이밍·로깅·예외 처리 등 [백엔드 가이드](../../development/04_BACKEND_GUIDE.md) 규칙을 따르고, 변경 범위를 기능 요구에 맞춰 최소화한다.

## 결정 2 — 가이드 수정·삭제 권한을 "소유자 + 관리자" 로 확대

- WEB(BFF)이 이미 모든 WAS 호출에 주입하는 **`X-User-Role` 헤더**를 WAS 가이드 컨트롤러가 수신한다.
- 관리자(`ADMIN`·`ROLE_ADMIN`)면 타인 문서도 수정·삭제를 허용한다(`findEditableGuide`). 일반 사용자는 종전대로 본인 문서만.
- 프론트는 **소유자 본인이거나 관리자일 때만** 수정·삭제 버튼을 노출한다(`canManage`). 서버가 최종 방어선이고, 프론트 노출은 UX일 뿐임을 전제로 **양쪽 기준을 일치**시킨다.

## 이유

- **방어선 일원화**: 권한 판단을 서버(WAS)가 최종 책임진다. 프론트 숨김은 보조 UX일 뿐, 우회(URL 직접 진입)에도 안전하다.
- **기존 인프라 재사용**: `X-User-Role`은 WEB이 이미 주입 중(채팅에서 사용). WEB은 손대지 않고 WAS 수신부만 추가하면 된다.
- **원칙의 현실화**: "무변경"이라는 이상보다, "주인공을 보호하되 필요하면 신중히 수정"이 실제 개발을 방해하지 않는다.

## 고려한 대안

| 대안                            | 기각 이유                                                                |
| ------------------------------- | ------------------------------------------------------------------------ |
| 프론트에서 버튼만 관리자에 노출 | WAS가 여전히 막아 관리자가 눌러도 실패 — 화면과 동작 불일치, 방어선 약화 |
| 관리자 허용을 포기(소유자만)    | 요구사항 미충족. 관리자 운영 기능이 필요                                 |
| WAS 대신 WEB에서 권한 판단·우회 | 3-tier 위반(로직이 표현/중계 계층으로 샘). 권한은 로직 계층(WAS) 책임    |
| 관리자 전용 별도 API 신설       | 현 규모엔 과설계. 기존 엔드포인트에 role 반영이 단순·충분                |

## 결과 (Consequences)

- ➕ 관리자 운영 기능을 안전하게(서버 방어) 구현. 프론트·백엔드 권한 기준 일치.
- ➕ 향후 WAS 개선(신규 기능·버그 수정)을 "무변경" 제약 없이 진행 가능.
- ➖ WAS도 회귀 위험 관리 대상이 됨 → 변경 시 테스트·리뷰로 보완(가이드 서비스 테스트 유지).
