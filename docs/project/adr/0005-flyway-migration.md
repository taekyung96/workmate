# ADR-0005. 스키마 관리를 Flyway 마이그레이션으로 전환

- **상태**: 채택
- **맥락 문서**: [11. 배포 가이드](../../development/11_DEPLOYMENT_GUIDE.md) · [12. 운영 가이드](../../development/12_OPERATIONS.md)
- **관련 ADR**: [ADR-0001](0001-hybrid-ssr-to-vue3-spa.md)(3-tier·WAS 은닉)

## 맥락 (Context)

스키마를 `db/init/*.sql` 파일 모음으로 관리해 왔다. 파일에 번호를 붙여 순서를 표현하고,
`ddl-auto: validate` 로 애플리케이션이 스키마를 건드리지 못하게 막는 구조였다.

문제는 **이 파일들을 적용하는 경로가 셋으로 갈라졌고, 셋 다 다르게 동작했다**는 것이다.

| 경로 | 방식 | 문제 |
| --- | --- | --- |
| 새 컨테이너 | Postgres 엔트리포인트가 알파벳순 실행 | **볼륨이 비어 있을 때만** 돈다 |
| CI | bash 루프로 `.sql` 만 적용 | `.sh` 는 건너뛴다 |
| 이미 뜬 서버 | 사람이 `docker exec psql` 로 누락분 수동 적용 | **무엇을 적용했는지 기록이 없다** |

세 번째가 실제로 문제를 일으켰다. 기존 볼륨이 있는 서버에 새 스크립트가 적용되지 않으면
`ddl-auto: validate` 가 실패해 WAS 가 기동조차 못 하는데, "이 서버에 몇 번까지 넣었나" 를
확인할 방법이 DB 를 직접 뒤지는 것뿐이었다. 배포 문서에 수동 적용 절차를 적어 두는 것으로
버티고 있었지만, 이건 사람의 기억에 기대는 방식이다.

## 결정 (Decision)

**Flyway 를 도입하고, 스키마 관리 경로를 하나로 합친다.**

마이그레이션은 `workmate-was/src/main/resources/db/migration/` 에 두고 **WAS 가 기동할 때**
미적용분을 순서대로 적용한다. 적용 이력은 DB 안 `flyway_schema_history` 에 남는다.

부수 효과가 하나 있다. 마이그레이션이 **jar 안에 포함**되므로, 배포 서버가 스키마를 얻기 위해
저장소를 클론할 필요가 없어진다(그전에는 `db/init` 이 필요해 클론이 필수였다).

### 세부 결정

**① 기존 16개 파일을 1:1 로 옮기지 않고 스냅샷으로 압축한다.**

파일들은 DDL 과 DML 이 섞여 있고 번호 접두사도 중복(`05-` 두 개)이었다. 손으로 옮겨 적으면
반드시 어딘가 틀린다. 대신 빈 컨테이너에 CI 와 같은 순서로 전부 적용한 뒤 `pg_dump` 로 떠서
두 개로 만들었다.

```
V1__baseline_schema.sql       pg_dump --schema-only  (테이블·인덱스·제약·코멘트 전부)
V2__seed_reference_data.sql   pg_dump --data-only    (guide·vector_store·common_code)
```

**검증**: 두 방식으로 각각 만든 DB 의 `pg_dump --schema-only` 결과가 1,193줄 전체에서
바이트 단위로 일치함을 확인했다. 옛 파일은 대조용으로 `db/init/legacy/` 에 남겨 두었다.

**② 이미 떠 있는 DB 는 baseline 으로 물려받는다.**

`baseline-on-migrate: true` · `baseline-version: 1` 로, 기존 DB 를 "V1 은 이미 적용됨" 으로
도장 찍고 V2 부터 진행시킨다. V2 는 모든 INSERT 에 `ON CONFLICT DO NOTHING` 을 붙여
**재실행해도 안전**하게 만들었다. 그래서 기존 DB 에 V2 가 다시 적용돼도 중복이 생기지 않는다.

**③ 데모 계정·콘텐츠는 마이그레이션에 넣지 않는다.**

데모 계정의 이메일·전화번호는 **AES 키로 암호화되어 저장**된다. 개발 키로 만든 암호문을
마이그레이션에 박아 두면, 다른 키를 쓰는 배포에서는 영원히 복호화되지 않는다.

대신 `scripts/bootstrap-demo-data.sh` 가 계정 생성·콘텐츠 시드·관리자 승격을 모두 맡는다.
**실제 AES 키를 쥔 쪽이 만들어야 처음부터 올바른 암호문이 들어가기 때문**이다.

부수 효과로 **공개 배포가 기본적으로 안전**해진다. 데모 관련은 아무것도 자동 실행되지 않고,
사람이 명시적으로 스크립트를 돌려야만 생긴다. 데모 비밀번호가 README 에 공개돼 있으므로
이 성질이 중요하다. 관리자 승격도 `--grant-admin` 옵트인으로만 일어난다.

## 고려한 대안

| 대안 | 기각 이유 |
| --- | --- |
| **Liquibase** | XML/YAML DSL 로 DB 중립성을 얻는 도구다. 여기선 PostgreSQL 하나만 쓰고, 기존 자산이 전부 순수 SQL 이라 얻는 것 없이 변환 비용만 든다 |
| **별도 Flyway 컨테이너** | 기동 순서를 compose 로 조율해야 하고 CI 에도 같은 걸 또 만들어야 한다. 앱 내장이면 세 경로가 자동으로 같아진다 |
| **dev 전용 마이그레이션 location** (데모 데이터용) | 그렇게 시드해도 암호문이 개발 키로 굳어 있어 결국 재암호화 스크립트를 또 돌려야 한다. **메커니즘만 둘로 늘고 문제는 그대로다** |
| **`ddl-auto: update` 로 전환** | 애플리케이션이 스키마를 바꾸게 되어 `validate` 를 쓰던 의도와 정면으로 충돌한다 |
| **현행 유지** | 위 맥락의 세 갈래 문제가 그대로 남는다 |

## 결과 (Consequences)

- ➕ **적용 이력이 DB 에 남는다.** "이 서버에 뭐가 적용됐나" 를 `flyway_schema_history` 로 답할 수 있다
- ➕ 새 컨테이너·CI·기존 서버가 **같은 경로**를 탄다. 수동 적용 절차가 사라졌다
- ➕ 마이그레이션이 이미지에 포함돼 배포 서버에 저장소 클론이 필요 없다
- ➖ **적용된 마이그레이션 파일은 수정할 수 없다.** 고치면 체크섬 불일치로 기동이 깨진다.
  스키마 변경은 항상 새 버전 파일을 추가하는 방식이어야 한다 (CLAUDE.md 에 명시)
- ➖ 기동 시점에 마이그레이션이 돌므로 첫 기동이 조금 느려진다

### 함정 — 플레이스홀더 치환

Flyway 는 기본적으로 SQL 안의 `${...}` 를 자기 플레이스홀더로 해석한다. 시드에 들어 있는
가이드 문서 본문에 GitHub Actions 예시(`${{ secrets.DOCKERHUB_USERNAME }}`)가 리터럴로
포함돼 있어 파싱 에러가 났다. 원래 쓰지 않는 기능이라 `placeholder-replacement: false` 로 껐다.

> 문서 내용을 시드로 넣는 프로젝트에서 반복될 수 있는 함정이다.

## 후속 과제

- [ ] `db/init/legacy/` 는 대조가 더 필요 없어지면 삭제한다
- [ ] 마이그레이션이 늘어나면 `V1` 스냅샷을 다시 뜨는 시점(squash)을 검토한다
