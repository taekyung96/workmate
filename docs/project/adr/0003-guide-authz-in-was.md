# ADR-0003. 권한 판정은 WAS 에서 — 가이드 수정·삭제를 소유자 + 관리자로

- **상태**: 채택
- **관련 문서**: [아키텍처](../../development/01_ARCHITECTURE.md) · [ADR-0001](0001-spa-bff-session-auth.md)

## 맥락

사내 가이드는 작성자 본인만 고치고 지울 수 있었다. 여기에 **관리자도 남의 가이드를 수정·삭제할 수 있어야 한다**는 요구가 더해졌다.

걸림돌은 WAS 가 받는 정보였다. WEB(BFF)은 로그인한 사용자를 `X-User-Seq` 헤더로 WAS 에 넘기는데,
가이드 API 는 이 값과 작성자가 같은지만 봤다. **WAS 쪽에는 이 사람이 관리자인지 알 수단이 없었다.**

가장 빠른 해결은 프론트에서 관리자에게도 수정 버튼을 보여 주는 것이다. 하지만 그러면 버튼은 보이는데
누르면 WAS 가 막는다. 반대로 WAS 검사를 느슨하게 하면, URL 을 직접 호출하는 사람은 버튼과 상관없이 통과한다.
**화면에 보이는 권한과 서버가 지키는 권한이 어긋나는 상태**를 만들고 싶지 않았다.

## 결정

- WEB 이 모든 WAS 호출에 이미 붙이고 있던 **`X-User-Role` 헤더**를 가이드 API 도 받는다(채팅에서 쓰던 헤더다)
- WAS 의 `findEditableGuide` 가 최종 판정한다 — 관리자면 모든 문서, 일반 사용자면 본인 문서만 통과
- 프론트의 `canManage` 는 같은 기준(본인 또는 관리자)으로 버튼만 보여 준다. 판정이 아니라 안내다

## 고려한 대안

| 대안                              | 기각 이유                                                                                                            |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| 프론트에서 버튼만 관리자에게 노출 | WAS 가 여전히 막아 관리자가 눌러도 실패한다. 화면과 동작이 어긋난다                                                  |
| WEB 에서 권한을 판단하고 통과시킴 | 권한은 비즈니스 규칙이다. 중계 계층에 로직이 새면 3-tier 가 무너지고, WAS 를 직접 부르는 경로가 생기면 그대로 뚫린다 |
| 관리자 전용 API 를 따로 만듦      | 같은 수정·삭제를 두 벌 유지해야 한다. 지금 규모에서는 기존 API 에 역할 하나를 더 보는 쪽이 단순하다                  |
| 관리자 허용을 포기                | 운영 요구를 못 채운다                                                                                                |

## 결과

- 좋은 점: 권한의 최종 책임이 WAS 한 곳에 있다. 프론트를 우회해 API 를 직접 불러도 같은 규칙이 적용된다
- 좋은 점: WEB 은 손대지 않았다. 이미 보내던 헤더를 WAS 가 읽기 시작했을 뿐이다
- 대가: `X-User-Seq`·`X-User-Role` 은 서명 없는 평문 헤더다. WAS 가 내부망에 있어 외부에서 위조할 수 없다는 전제에 기댄다
