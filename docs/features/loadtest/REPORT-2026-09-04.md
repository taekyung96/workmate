# 부하 테스트 리포트 (2026-09-04)

읽기 경로의 처리 한계를 재고, Redis 도입 목표였던 **"인스턴스를 늘려도 세션이 유지되는가"** 를
부하 중에 확인한다.

- 스크립트: [`scripts/loadtest/api-load.js`](../../../scripts/loadtest/api-load.js)
- 실행: `docker run --rm --network host -v "$PWD/scripts/loadtest:/s" grafana/k6 run /s/api-load.js`

---

## 1. 먼저 밝혀 둘 한계

**부하 생성기와 대상 서버가 같은 머신이다.** k6·WEB·WAS·PostgreSQL·Redis 가 WSL2 의 같은 8코어를
나눠 쓴다. 따라서 아래 **처리량 수치는 이 머신의 총량 한계**이지 애플리케이션의 상한이 아니며,
**인스턴스를 늘렸을 때의 처리량 비교는 성립하지 않는다**(코어를 더 잘게 쪼갤 뿐이다).

측정 환경: WSL2 · 8 vCPU · RAM 7.6GB · Docker Desktop · pgvector/pgvector:pg17 · Redis 7

---

## 2. 무엇을 재고 무엇을 재지 않았나

| 대상                                | 경로                              | 이유                                                             |
| ----------------------------------- | --------------------------------- | ---------------------------------------------------------------- |
| `GET /api/auth/me`                  | 브라우저 → WEB → Redis            | 세션 조회. WAS·DB 를 타지 않아 **세션 계층만** 분리해 볼 수 있다 |
| `GET /api/v1/guides?page=0&size=10` | 브라우저 → WEB → WAS → PostgreSQL | 전체 경로                                                        |

**채팅·도우미는 제외했다.** 실제 LLM 을 부르므로 (1) 무료 티어 한도를 테스트가 소모하고
(2) 응답 시간이 모델·네트워크에 좌우돼 우리 스택의 처리량을 잴 수 없으며
(3) 사용자당 분당 레이트리밋에 먼저 걸린다. 알고 싶은 것은 우리 서버의 한계지 제공자의 속도가 아니다.

## 3. 단일 인스턴스 — 어디까지 버티나

|  VU |    처리량 |   실패 | `/auth/me` p95 | `/guides` p95 |
| --: | --------: | -----: | -------------: | ------------: |
|  50 | 370 req/s | **0%** |          119ms |         163ms |
| 200 | 506 req/s | **0%** |          505ms |         740ms |

**오류로 무너지지 않고 지연으로 밀린다.** VU 를 4배로 올려도 실패는 0 이고 처리량은 1.37배만
늘었다 — 약 **500 req/s 부근에서 포화**한다.

부하 중 CPU:

```
workmate-web    ~300%      (3 코어)
workmate-was    ~240%      (2.4 코어)
workmate-db      ~43%
workmate-redis   ~22%
                 -----
합계            ~6.1 / 8 코어   (나머지는 k6 가 쓴다)
load average 42.8
```

포화의 원인은 **CPU** 다. 메모리(WAS 994MB · WEB 917MB)는 여유가 있었다.

## 4. WEB 2대 — 세션은 인스턴스를 건너 유지되는가

로드밸런서 없이 k6 가 VU 를 두 인스턴스에 나눠 붙였다(`TARGETS` 에 두 주소).

**결과: 32,718개 검사 전부 통과, 실패 0.** `/auth/me` 가 어느 인스턴스로 가든 같은 세션으로
인증됐다. Redis 세션 공유가 **부하 중에도** 동작한다 — ADR-0006 의 목표가 검증됐다.

| 구성 (200 VU) |    처리량 | 실패 | `/auth/me` p95 | `/guides` p95 |
| ------------- | --------: | ---: | -------------: | ------------: |
| WEB 1대       | 506 req/s |   0% |          505ms |         740ms |
| WEB 2대       | 167 req/s |   0% |      **325ms** |       3,450ms |

숫자가 갈렸다. **세션만 읽는 `/auth/me` 는 빨라졌고(505 → 325ms), 전체 경로는 크게 느려졌다.**

### 왜 처리량이 떨어졌나 — 두 가지가 겹쳤다

**(1) 코어는 그대로다.** 2대 구성에서도 총 CPU 는 같은 수준이었다.

```
web-1 ~150-198%  +  web-2 ~149-152%   →  합쳐서 단일 WEB(~300%) 과 같다
was-1 ~190-236%                        →  WAS 는 여전히 1대
db ~28-51%   redis ~34-54%
```

WEB 을 늘려도 나눠 갖는 코어 총량이 같으니 처리량이 늘 수 없다. 그리고 **WAS 는 1대 그대로인데
프록시가 둘로 늘어** 더 많은 동시 요청을 받는다. 병목이 WEB 에서 WAS 로 옮겨간 것이 `/guides` p95
3.45초로 나타났다.

**(2) 테스트가 세션 하나를 공유한다.** WEB 은 중복 로그인을 막으므로(`maximumSessions(1)`)
VU 마다 로그인하면 서로의 세션을 만료시킨다. 그래서 setup 에서 한 번 로그인한 쿠키를 모든 VU 가
공유한다. 그 결과 **모든 요청이 Redis 의 같은 세션 키 하나를 갱신**한다(Spring Session 은 요청마다
lastAccessedTime 을 쓴다). 인스턴스가 둘로 늘자 그 한 키에 대한 경합이 커졌고, Redis CPU 가
22% → 54% 로 배 이상 뛴 것이 그 흔적이다.

즉 **이 표의 처리량 차이는 애플리케이션의 확장성이 아니라 측정 환경과 테스트 설계의 한계**다.
확장성을 숫자로 증명하려면 아래가 필요하다.

## 5. 다음에 제대로 재려면

1. **부하 생성기를 다른 머신으로** 분리한다. 지금은 k6 가 대상과 코어를 다툰다
2. **세션을 여러 개로** 만든다. 사용자를 여러 명 만들거나 중복 로그인 제한을 테스트 프로파일에서만
   풀어, Redis 키가 흩어지게 한다 — 실제 트래픽의 모양이다
3. **WEB 과 WAS 를 함께** 늘린다. WEB 만 늘리면 병목이 WAS 로 옮겨갈 뿐이다
4. 앞에 **로드밸런서**를 둔다. 지금은 k6 가 VU 를 나눠 붙여 흉내만 냈다

## 6. 지금 말할 수 있는 것

- 이 머신에서 읽기 경로는 **약 500 req/s** 까지 오류 없이 처리하고, 그 뒤로는 지연으로 밀린다
- 한계 요인은 **CPU** 다. 메모리는 여유가 있었다
- **Redis 세션 공유는 부하 중에도 인스턴스를 건너 동작한다** — 실패 0, 검사 32,718건 전부 통과.
  이것이 이번 측정에서 환경 제약과 무관하게 유효한 결론이다
- 세션만 읽는 경로는 WEB 을 늘리자 **p95 505ms → 325ms 로 개선**됐다. 확장이 듣는 구간이 있다는
  신호이긴 하나, 같은 머신에서 잰 값이라 배포 환경의 수치로 인용하면 안 된다
