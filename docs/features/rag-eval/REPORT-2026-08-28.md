직전 실행은 주제가 뚜렷이 갈린 17개 코퍼스라 **전 구간 Hit@K·MRR 100%로 포화**됐고, `topK`·`threshold` 를 바꿔도 결과가 변하지 않아 튜닝 여지가 드러나지 않았다. 코퍼스를 34개로 늘리고(주제가 겹치는 문서 추가) 골든셋을 33문항으로 확장하자 두 가지가 처음으로 관찰된다.

1. **MRR 1.000 → 0.970** — 정답 청크가 항상 1위는 아니게 됐다. 주제가 인접한 문서끼리 경쟁하기 시작했다는 뜻이다.
2. **threshold 0.60에서 Hit@K 97.0%** — 임계값을 올리면 재현율이 깎인다. 0.30~0.50 구간은 여전히 100%다.

`topK` 는 2~8 전 구간에서 결과가 같다. 정답이 상위 2건 안에 들어오므로 후보를 더 늘려도 얻는 게 없다는 뜻이며, 후보를 늘릴수록 프롬프트 토큰만 증가한다.

→ **운영 기본값 `topK=4` · `threshold=0.4` 는 이 코퍼스에서 재현율 손실 없이(Hit@K 100%) 동작한다.** threshold 를 0.6까지 올리면 재현율을 잃고, topK 를 8까지 올리면 비용만 는다. 이전 리포트에서는 "포화라 안전해 보인다" 수준이었으나, 이번 실행으로 **양쪽 방향의 손해를 실제로 측정해 기본값을 뒷받침**했다.

## 부수 소득 — 하네스가 코퍼스 결함을 잡아냈다

재평가 첫 시도에서 Hit@K 51.5%가 나왔는데, `topK` 2·4·6·8에서 값이 **완전히 동일**했다. topK 를 늘리면 후보가 늘어 Hit@K 는 올라가야 정상이므로, 이 평탄한 형태는 검색 성능 저하가 아니라 **정답 문서가 코퍼스에 아예 없다**는 신호였다. 확인 결과 시드 가이드 17개 중 7개만 DB 에 남아 있었다(볼륨 재사용 과정에서 유실). `seedGuides` 로 10개를 보충하니 위 결과가 나왔다.

즉 이 하네스는 검색 품질뿐 아니라 **코퍼스 무결성 회귀**도 잡는다. 지표를 조합별로 훑어 두면 단일 숫자로는 안 보이는 결함이 형태로 드러난다.
