# Redis 분산 상태 저장소 도입 전후 검증 리포트

- 실행일: 2026-09-02
- 대상: 세션 · `SessionRegistry`(F1-08 중복 로그인 차단) · `ChatRateLimiter`(F2-11)
- 관련: [ADR-0006](../../project/adr/0006-redis-distributed-state.md)

## 요약

인스턴스를 2개로 늘렸을 때 세 가지가 **에러 없이 조용히** 깨지는 것을 재현하고, Redis 도입 후 해소된 것을 확인했다.

| #   | 항목                       | 도입 전                              | 도입 후                | 판정 |
| --- | -------------------------- | ------------------------------------ | ---------------------- | :--: |
| ①   | 인스턴스 간 세션 유지      | **401** (다른 인스턴스에서 로그아웃) | **200**                |  ✅  |
| ②   | 중복 로그인 차단 (F1-08)   | **두 세션 모두 200** (무력화)        | **첫 세션 401** (축출) |  ✅  |
| ③   | 분당 한도 5 · 인스턴스 2개 | **10건 통과** (정확히 2배)           | **6회째 429**          |  ✅  |
| ④   | 레이트리밋 키 TTL          | 없음 (키가 힙에 영구 누적)           | **49초** (상한 90초)   |  ✅  |

**①②③ 모두 예외나 에러 로그를 남기지 않는다.** 로그만 봐서는 정상으로 보이는 것이 이 결함의 핵심이다.

## 측정 조건

- 호스트: Windows 10 · WSL2 (Ubuntu) 안의 Docker
- 스택: `docker compose -f docker-compose.yml -f docker-compose.scale.yml --profile full up -d --scale web=2 --scale was=2`
- Redis: `redis:7-alpine` (`appendonly yes`), DB: `pgvector/pgvector:pg17`
- 계정: `demo.admin@example.com` (userSeq 12) — README 에 공개된 데모 계정
- 레이트리밋 한도: **5/분** (기본 20 을 낮춰 측정 시간을 줄임, `SCALE_TEST_RATE_LIMIT`)

### "도입 전" 을 어떻게 잰 것인가

**추정이 아니라 실제로 옛 코드를 돌려서 쟀다.** 두 가지 방법을 항목별로 나눠 썼다.

| 항목               | 방법                                                                                 | 근거                                                                                                     |
| ------------------ | ------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------- |
| ①② 세션·레지스트리 | **Redis 이전에 빌드된 이미지** `workmate-v3-web:latest`(2026-08-31 빌드) 를 2개 띄움 | 이미지의 `app.jar` 를 풀어 확인: `spring-session`·`spring-data-redis`·`RedisSessionConfig` **모두 없음** |
| ③ 레이트리밋       | 현재 이미지에서 `RATE_LIMIT_STORE=memory` 로 전환                                    | 측정 중 Redis 에 `workmate:ratelimit:*` 키가 **0개** — 인메모리 구현이 실제로 쓰였다는 증거              |

이미지 검증에 쓴 명령:

```bash
CID=$(docker create workmate-v3-web:latest)
docker cp "$CID":/app/app.jar /tmp/old-web.jar && docker rm "$CID"
python3 -c "
import zipfile
n = zipfile.ZipFile('/tmp/old-web.jar').namelist()
print('spring-session    :', [x for x in n if 'spring-session' in x] or '없음')
print('spring-data-redis :', [x for x in n if 'spring-data-redis' in x] or '없음')
print('RedisSessionConfig:', [x for x in n if 'RedisSessionConfig' in x] or '없음')"
```

## ① 인스턴스 간 세션 유지

인스턴스1 에 로그인한 뒤 **같은 쿠키로 인스턴스2** 에 조회한다.

```bash
curl -s -c c1.txt "http://localhost:$P1/api/auth/me" > /dev/null
X=$(grep XSRF-TOKEN c1.txt | awk '{print $7}')
curl -s -b c1.txt -c c1.txt -X POST "http://localhost:$P1/api/auth/login" \
     -H "X-XSRF-TOKEN: $X" \
     --data-urlencode "email=demo.admin@example.com" \
     --data-urlencode "password=Workmate!2026"
curl -s -o /dev/null -w "%{http_code}\n" -b c1.txt "http://localhost:$P2/api/auth/me"
```

|         | 인스턴스1 (로그인한 곳) | 인스턴스2 (같은 쿠키) |
| ------- | :---------------------: | :-------------------: |
| 도입 전 |           200           |        **401**        |
| 도입 후 |           200           |        **200**        |

> 로그인 요청은 `application/x-www-form-urlencoded` 다. `SecurityConfig` 의
> `.loginProcessingUrl("/api/auth/login").usernameParameter("email")` 을 Spring Security 가 처리하므로
> JSON 으로 보내면 _"이메일을 입력해주세요"_ 로 거절된다.

도입 후 Redis 에 실제로 저장된 키:

```
workmate:session:sessions:0c0b30e7-...
workmate:session:sessions:expires:2d176aff-...
workmate:session:index:org.springframework.session.FindByIndexNameSessionRepository.PRINCIPAL_NAME_INDEX_NAME:...
```

**세 번째 `PRINCIPAL_NAME_INDEX_NAME` 키가 중요하다.** 이 인덱스는
`spring.session.redis.repository-type: indexed` 일 때만 만들어지고, ② 가 이 인덱스에 의존한다.
기본값(`default`)으로 두면 이 키가 없고 ② 가 **조용히** 실패한다.

## ② 중복 로그인 차단 (F1-08)

같은 계정으로 **다른 인스턴스에** 새로 로그인한 뒤, 첫 세션이 축출됐는지 본다.

|         | 첫 세션 (인스턴스1) | 새 세션 (인스턴스2) |
| ------- | :-----------------: | :-----------------: |
| 도입 전 | **200** ← 살아있음  |         200         |
| 도입 후 |  **401** ← 축출됨   |         200         |

도입 후에는 첫 세션 쿠키를 **인스턴스2 에 물어봐도 401** 이다 — 판정이 한 곳에서 나온다.

> 도입 전 상태가 위험한 이유: 사용자는 로그아웃된 줄 알지만 이전 세션이 다른 인스턴스에서 계속 살아있다.
> 계정 도용 시 세션을 끊었다고 생각해도 실제로는 안 끊긴다. **예외도 경고 로그도 없다.**

## ③ 레이트리밋 (F2-11)

**레이트리미터는 WAS 에 있다.** WEB 만 2개로 늘려서는 검증되지 않아 **WAS 를 2개**로 띄우고
각 인스턴스에 직접 요청했다(`X-User-Seq` 헤더로 신원 전달, WEB 을 거치지 않음).

```bash
for i in $(seq 1 8); do
  PORT=$([ $((i % 2)) -eq 0 ] && echo $W1 || echo $W2)
  curl -s -N -o /dev/null --max-time 2 -w "$i -> %{http_code}\n" \
       -X POST "http://localhost:$PORT/api/v1/chat/stream" \
       -H "Content-Type: application/json" -H "X-User-Seq: 12" \
       -d '{"message":"ping"}'
done
```

### 도입 전 — 인메모리 (`RATE_LIMIT_STORE=memory`)

```
1~10회  통과
11회    429
12회    429
```

**한도가 5인데 10건이 통과했다 — 정확히 인스턴스 수만큼 곱해졌다.**
측정 중 Redis 의 `workmate:ratelimit:*` 키는 **0개**였다(인메모리가 쓰였다는 증거).

### 도입 후 — Redis

```
1~5회   통과   (was-2 에 3건, was-1 에 2건)
6회     429    ← was-1 은 자기 카운터로는 2건만 봤는데 막혔다
7,8회   429
```

Redis 키:

```
workmate:ratelimit:12:29805458 = 8
```

**키 하나에 8이 누적됐다.** 두 WAS 인스턴스가 같은 카운터를 증가시킨다는 직접 증거다.
6회차 요청은 was-1 으로 갔는데, 인메모리였다면 was-1 은 로컬 카운터가 2뿐이라 **통과시켰을 것**이다.

> **`--max-time 2` 를 쓰는 이유.** 통과한 요청은 SSE 스트림을 열고 LLM 응답을 기다리므로 오래 걸린다.
> 레이트리밋 카운터는 스트림을 열기 **전에** 증가하므로 짧게 끊어도 측정에 영향이 없다.
> 반대로 차단된 요청은 LLM 을 부르지 않아 429 가 즉시 온다.
> 첫 시도에서 `--max-time 12` 로 쟀더니 8회 요청이 분 경계를 넘어 카운터가 `5 + 3` 으로 쪼개졌다 —
> **측정 전에 새 분이 시작될 때까지 기다려야 한다.**

## ④ 레이트리밋 키 TTL

```
workmate:ratelimit:12:29805458   값=8   TTL=49초
workmate:session:sessions:0c0b...        TTL=1661초  (≈28분, 세션 타임아웃 30분)
```

인메모리 구현은 `ConcurrentHashMap` 의 `userSeq` 키를 **한 번도 지우지 않는다** — 분이 바뀌면
값 객체만 교체되고 키는 남아 사용자 수만큼 힙이 단조 증가한다. Redis 구현은 첫 증가에서
`EXPIRE` 를 걸어 이 누수가 없다.

## 이 검증에서 발견한 결함 — `REDIS_HOST` 누락

**단위·통합 테스트 137건이 전부 통과했는데도 컨테이너로 띄우니 뜨지 않았다.**

```
Caused by: io.lettuce.core.RedisConnectionException:
    Unable to connect to localhost/127.0.0.1:6379
```

`application.yml` 의 기본값이 `${REDIS_HOST:localhost}` 인데 compose 에 `REDIS_HOST` 를 주지 않았다.
**컨테이너 안에서 `localhost` 는 자기 자신**이라 Redis 컨테이너에 닿지 못한다.
`docker-compose.yml`·`docker-compose.deploy.yml` 양쪽의 `was`·`web` 에 `REDIS_HOST: redis` 를 추가해 고쳤다.

### 두 모듈의 증상이 정반대였다

|         | 증상                                                                          | 이유                                                               |
| ------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| **WEB** | 기동 자체가 실패 (`enableRedisKeyspaceNotificationsInitializer` 빈 생성 실패) | 세션은 **fail-closed** — Redis 가 없으면 로그인이 불가능한 게 맞다 |
| **WAS** | **정상 기동.** 로그에 아무 이상 없음                                          | 레이트리밋은 **fail-open** — Redis 장애로 채팅 전체를 막지 않는다  |

의도한 설계대로 동작한 것이지만, **WAS 쪽 오설정은 아무도 모르는 채로 넘어간다**는 뜻이기도 하다.
레이트리밋이 사실상 꺼진 상태로 운영될 수 있다. 이 리스크는 ADR-0006 D4 에 기록했다.

> 이 결함은 **테스트로는 잡히지 않는다.** 테스트는 `localhost:6379` 가 맞는 환경에서 돌기 때문이다.
> 컨테이너로 실제로 띄워보는 이 검증 단계가 없었으면 배포에서 처음 발견됐을 것이다.

## 재현 방법

`docker-compose.scale.yml` 이 이 검증 전용 오버라이드다. 개발 compose 는 WEB·WAS 에
고정 이름(`container_name`)과 고정 포트를 주는데 둘 다 `--scale` 을 막으므로, 그것만 걷어낸다.

```bash
# 도입 후 (현재 코드)
docker compose -f docker-compose.yml -f docker-compose.scale.yml --profile full \
    up -d --build --scale web=2 --scale was=2

# 각 인스턴스의 호스트 포트 확인
docker compose -f docker-compose.yml -f docker-compose.scale.yml --profile full ps

# 도입 전 재현 — 레이트리밋
SCALE_TEST_RATE_LIMIT_STORE=memory docker compose ... up -d --scale was=2

# 도입 전 재현 — 세션 (Redis 이전 이미지)
SCALE_TEST_WEB_IMAGE=workmate-v3-web:latest docker compose ... up -d --scale web=2
```

### 환경 주의사항

- **WSL2 가 유휴 상태에서 스스로 종료되면 컨테이너가 함께 죽는다.** 종료코드가 `143`(SIGTERM)이 아니라
  **`0`** 인 것이 이 현상의 표시다. 측정이나 테스트가 몇 분 이상 걸리면 WSL 세션을 하나 붙잡아 둬야 한다
  (`wsl -e bash -lc 'sleep 1500'`). 실제로 이 때문에 백엔드 테스트 137건 중 11건이
  "실패"로 나온 적이 있다 — 코드 문제가 아니었다.
- Gradle 은 Windows 에서, Docker 는 WSL2 에서 돈다. 테스트가 Redis·PostgreSQL 에 붙는 경로는
  **WSL2 의 localhost 포워딩**이다(`application-local.yml` 의 DB 접속과 같은 방식).
